## Context

The `go-zero-boilerplate` monorepo enforces a strict architectural boundary:
- Only `app/gateway` exposes HTTP RESTful endpoints (Port 8888).
- Internal services (`user`, `worker`) are pure gRPC services.
- Frontends (`admin`, `portal`) consume the typed SDK `@zero/api` generated by `just gen-ts`.

See `proposal.md` for motivation. This design implements the navigation hub cleanly within these established guardrails.

## Goals / Non-Goals

**Goals:**
- Provide a clean, read-only responsive navigation page in `@zero/portal` (`/navigation`) with categories, live search, and dynamic `{HOST}` interpolation.
- Provide a full-lifecycle CRUD administration page in `@zero/admin` (`/system/navigation`) with ProTable, ModalForm, sorting weight, and status toggles.
- Implement MySQL DDL migration, Redis Cache-Aside retrieval, gRPC RPC methods, and Gateway BFF endpoints.
- Auto-generate TypeScript client functions in `@zero/api` using `just gen-ts`.
- Ensure 0 Ant Design 6 lint warnings (`just lint-antd`) and 100% test pass rate (`just test-frontend`).

**Non-Goals:**
- Providing reverse proxying, iframe embedding, or SSO credential injection into third-party target URLs (sites open natively via browser tabs).
- Multi-tenant site partitioning or per-department link visibility access control (internal tools are accessible globally to all staff/developers).

## Decisions

### 1. Schema Modeling: Single-Table Architecture (`sys_portal_nav`)
- **Decision**: Store navigation sites in a single table `sys_portal_nav` with an indexed `category` string column.
- **Rationale**: The number of internal enterprise technical tools is typically tens to hundreds. A single table avoids multi-table joins and simplifies both Admin ProTable and Portal grouping.
- **Alternatives Considered**: Creating separate `sys_nav_category` and `sys_nav_item` tables. Rejected because category management overhead outweighs the benefit for technical navigation.

### 2. Microservice Placement: User RPC Service
- **Decision**: Place the persistence model and gRPC logic within `app/user/rpc`.
- **Rationale**: `user` service is already the designated domain service for system governance and metadata (`sys_notice`, `sys_dict`, `sys_config`, `sys_post`).
- **Alternatives Considered**: Creating a standalone `nav` microservice. Rejected as it would introduce excessive container and gRPC port overhead for a metadata feature.

### 3. Dynamic Host Resolution: `{HOST}` Placeholder
- **Decision**: Allow storing `{HOST}:8233` or `{HOST}:8848` in the URL column, with the Portal frontend replacing `{HOST}` with `window.location.hostname`.
- **Rationale**: Allows the same navigation database records to work whether accessed via `localhost`, local Wi-Fi LAN IP (e.g. `192.168.31.174:3000`), or remote server domains, without manual database environment rewrites.
- **Alternatives Considered**: Storing relative paths or maintaining environment-specific database seeds. Rejected due to poor portability across environments.

### 4. Dynamic Icon Rendering: Hybrid Registry + Image URL
- **Decision**: Support both Ant Design icon identifiers (e.g. `CloudServerOutlined`, `ClusterOutlined`, `CompassOutlined`, `ApiOutlined`, `DashboardOutlined`, `ToolOutlined`) and direct image/SVG URLs.
- **Rationale**: Users can choose built-in icons effortlessly from a dropdown or input SVG/PNG URLs for specialized tools (e.g. Jenkins, Prometheus, Kafka).
- **Alternatives Considered**: Strictly allowing custom image uploads. Rejected due to asset storage overhead for simple system links.

### 5. Caching Strategy: Redis Cache-Aside
- **Decision**: Cache the enabled navigation dataset under Redis key `cache:portal:navigation:all`.
- **Rationale**: Portal navigation is read-heavy and updated infrequently. Caching guarantees sub-millisecond retrieval on the portal while Admin mutations (`Create`, `Update`, `Delete`) perform precision cache eviction.

## Risks / Trade-offs

- **[Risk] Invalid or broken target URLs entered by administrators** → Mitigation: Admin form validates URL format using regex patterns accepting `http://`, `https://`, and `{HOST}:port`.
- **[Risk] Stale cache on Portal when database is updated directly** → Mitigation: In addition to RPC-level precision eviction, provide a short default TTL (e.g., 1 hour) or an Admin "refresh cache" action if needed.
- **[Risk] Ant Design 6 Icon tree-shaking overhead** → Mitigation: Implement a curated icon lookup dictionary in Portal rather than dynamically importing the entire `@ant-design/icons` library.

## Migration Plan

1. Create migration SQL file `manifest/sql/migrations/<timestamp>_create_sys_portal_nav.sql`.
2. Apply migration to local MySQL via `atlas migrate apply --env local`.
3. Reverse-engineer Go Model via `goctl model mysql ddl` into `app/user/model`.
4. Update `app/user/rpc/user.proto` and run `just gen-rpc user`.
5. Update `app/gateway/desc/` and run `just gen-gateway`.
6. Run `just gen-ts` to regenerate `@zero/api`.
7. Implement frontend pages in `@zero/admin` and `@zero/portal`.
8. Run automated tests and lint checks.
